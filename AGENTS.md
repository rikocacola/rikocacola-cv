# Working agreements

Project background, the directory map, and the token table are in `CLAUDE.md`.
Read it before your first change. What follows is what to do and what not to do.

## Before you say you're done

Run all three. A change isn't finished until they pass:

```bash
npx tsc --noEmit
npm run lint
npm run build
```

If you touched anything visual, also load `/dashboard` and look at it at 390px
and 1440px. A build that compiles can still be broken.

## Hard rules

**Never use a relative parent import.** Use `@/…`. ESLint fails the build on
`../`. The exception is `src/components/ui/`, which is vendored shadcn code.

**Never write a colour value in a component.** No hex, no `rgb()`, no named
colours. Every colour comes from a `--brand-*` token or a Tailwind utility
bound to one (`bg-brand-surface`, `text-brand-accent`, `border-brand-line`). If
you need a shade that doesn't exist, add a token to `src/app/globals.css` and
explain why — don't inline it.

**Never import `@/data/profile` from a component.** Only
`src/app/dashboard/page.tsx` reads data. Components take props. If a component
needs new data, add a prop and thread it through the page. This is the whole
reason the sections are reusable.

**Don't hand-edit `src/components/ui/`.** Those files are regenerated by
`npx shadcn@latest add …`. Wrap them or compose around them instead. If a
primitive genuinely needs changing, say so rather than quietly patching it.

**Don't loosen the CSP.** `next.config.ts` is first-party-only by design. A new
font host, script, or remote image means a deliberate CSP change — flag it, and
prefer a local asset.

**Don't introduce `dangerouslySetInnerHTML`.**

**npm only.** If a tool tries to install with pnpm or yarn, delete the stray
lockfile and re-run `npm install`. Two lockfiles is a broken tree.

**Keep the image runnable.** If you add a file the server needs at runtime,
check it survives into `.next/standalone` — the Dockerfile only copies
`public/`, `.next/standalone`, and `.next/static`. New env vars that the
browser reads must be `NEXT_PUBLIC_*` **and** wired through as a Docker
`ARG`/`ENV` in the builder stage, because they're inlined at build time.

## Adding to the UI

Reach for `common/` first — `Panel`, `SectionHeader`, `StatItem`, `Chip`,
`LogoTile`, `BrandIcon`, `AvailabilityBadge` already exist. A new section
should mostly be composition. Only add to `common/` when the piece is generic
enough that it knows nothing about this particular CV.

A new section needs: a `Panel` with `as="section"`, an `id` that matches an
entry in `src/components/layout/nav-items.ts`, an `aria-labelledby` pointing at
its `SectionHeader` id, and an `index` prop for its place in the load stagger.

Prefer server components. Add `"use client"` only when you need state, effects,
or event handlers — right now that's `SiteNav`, `MobileNav`, and the shadcn
primitives.

## Quality floor

Not optional, and not worth announcing in the UI:

- Works down to 375px.
- Visible keyboard focus. The global `:focus-visible` rule handles it — don't
  remove outlines.
- Every interactive element reachable by tab, with an accessible name.
  Icon-only controls need `sr-only` text.
- Decorative images get `alt=""`; meaningful ones get real alt text.
- `prefers-reduced-motion` is respected globally in `globals.css`. Don't add
  animation that escapes it.
- Check contrast against the navy surfaces. Several brand logos are near-black
  and need the light plate `LogoTile` gives them.

## Writing copy

Plain and specific, sentence case, active voice. Say what something is, not how
good it is. "Built and maintained the sales operation web application" beats
"Leveraged cutting-edge technologies." No filler, no marketing register.

Content is real. Don't invent metrics, employers, dates, or projects to fill a
layout — if a section looks thin, change the layout or ask.
